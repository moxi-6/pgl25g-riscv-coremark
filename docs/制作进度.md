## CoreMark 移植完成、两种位流已出、待上板跑分（2026-10-22 夜）

上游 CoreMark 仓库只有 `v1.01` 一个 tag（`cfa9ab3778`，归档 SHA256 `99C5A6D63AF85A281B4E4D6CCB522C446653C435DFEC9455AD73EF9E71F28BDE`，401208 字节）；v1.0 的所有历史下载链接均已 404，实际移植的是 **v1.01**。

移植层落在 `software/coremark/`：EEMBC 原文件（`core_main.c`/`core_list_join.c`/`core_matrix.c`/`core_state.c`/`core_util.c`/`coremark.h`）逐字未改，只替换 `core_portme.[ch]`、`ee_printf.c`，另加 `softmath.c` 与 `board_coremark_config.h`。选 `MEM_STATIC`（栈只有 1 KiB，放不下 2000 字节缓冲）、`TOTAL_DATA_SIZE 2000`（对应 `seedcrc 0x18f2` 与 `size 666`）。

核心难点是 **RV32I 没有 M 扩展**：`rtl/core/rv32i_alu.sv` 只有加减移位逻辑，全工程 grep `MUL|DIV` 零匹配。CoreMark 的矩阵乘法与 `core_list_join.c` 必然用到乘除，而项目 `LDFLAGS` 明确 `-nostdlib`，所以没有改走 libgcc，而是自写 `softmath.c` 提供 `__mulsi3`/`__udivsi3`/`__umodsi3`/`__divsi3`/`__modsi3`（移位加减法循环），保证产物不引入任何被 `verify_firmware.py` 拒绝的指令。第二大发现是 **GCC 在 RV32I 上即使除数是常量也不做强度削减**（反汇编证据 `li a1,10; call __umodsi3`），因此 `ee_printf` 与 `time_in_secs` 里的十进制转换、秒数换算全部改写为 pow10 表减法循环，避免 64 位除法拉入 `__udivdi3`。

容量：CoreMark 板级镜像 ROM 13044 字节、data 1612、bss 2676。原 `RAM ORIGIN = 0x2000 LENGTH = 8K` 会让 `.data` VMA 与 `.text` 重叠，已改为给 DMEM 加高位别名（`__ram_alias_start = 0x20000000`），与既有 ROM 数据别名同法；`.text` 可完整用满 16 KiB IMEM。**该 RTL/链接脚本改动后 13 项原有回归零回归。**

验证：三算法 CRC 与 EEMBC 公布值逐一相符——`crclist 0xe714`、`crcmatrix 0x1fd7`、`crcstate 0x8e3a`、`seedcrc 0x18f2`、`CoreMark Size 666`；`tb_coremark` 断言 GPIO=0xa5、未 trap、三项 CRC 与 `seedcrc` 全部相符。完整 iverilog 回归由 13 项增至 **14 项全部通过**。单次迭代实测 **2,972,310 周期**（50 MHz 下 0.0594 秒），据此推算自动标定收敛到 300 次迭代、约 17.8 秒、约 16.8 iterations/sec。

**尚未成立：实板跑分未做。** 上述分数与迭代数是周期数的算术外推，不是硅上测量；仿真时钟下跑完一次真实运行需数亿周期，墙钟代价不可接受（实测约 3.5 万周期/秒），故仿真回归只跑钉死 1 次迭代的镜像。两个位流都已生成但均未下载：`build/board_release/cpu/coremark/atk_l50_top.sbit`（SHA256 `11C3A4B9…F4C76B`，1826 LUT / 1395 FF / 16 DRM18K）与 `build/board_release/cpu/perf_report/atk_l50_top.sbit`（SHA256 `70FDB495…3CA816`），两者时序均 `All Constraints Met.`。下载必须走 PDS GUI（命令行 GOUTEN 问题未解），COM8 抄录输出。

本轮另修掉四个会让既有 CPU 发布流程静默失效的预存 bug，其中最危险的是发布包会把选中的固件从源码树被遗留的 main 镜像覆盖回去（日志与 manifest 都显示成功）。详见 `交接记录/2026-10-22_CoreMark移植/验证说明.md`。
