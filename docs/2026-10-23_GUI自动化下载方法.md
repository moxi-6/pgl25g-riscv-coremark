本文记录如何用程序化方式驱动 PDS 的 Fabric Configuration 工具，替代人工点

## 1. 核心突破：GUI 内置 TCL 控制台

Fabric Configuration 窗口底部有一个 `TCL` 输入框（类名 `cfgTextEdit`），它就是
`cdt_cfg_shell.exe` 的交互式版本，可执行全部 60 条 `cfg_*` 命令。

**关键价值**：这个控制台运行在 GUI 自己的进程里，使用 GUI 的会话状态，因此
**不存在 CLI 与 GUI 的差异**（例如 `gouten` 门控、cable 属性、连接状态）。

### 驱动方式

```powershell
Add-Type -AssemblyName UIAutomationClient
Add-Type -AssemblyName UIAutomationTypes

$HWND = [IntPtr]3736034          # Fabric Configuration 窗口句柄
$w0 = [System.Windows.Automation.AutomationElement]::FromHandle($HWND)

# 找到 TCL 输入框
$edit = $null
foreach ($e in $w0.FindAll([System.Windows.Automation.TreeScope]::Descendants,
         [System.Windows.Automation.Condition]::TrueCondition)) {
    if ($e.Current.ClassName -eq 'cfgTextEdit') { $edit = $e }
}
$er = $edit.Current.BoundingRectangle
$cx = [int]($er.X + $er.Width/2)
$cy = [int]($er.Y + $er.Height/2)

# 读控制台输出：同一个 cfgTextEdit 的 TextPattern
function Console-Text {
    $ww = [System.Windows.Automation.AutomationElement]::FromHandle($HWND)
    foreach ($e in $ww.FindAll([System.Windows.Automation.TreeScope]::Descendants,
             [System.Windows.Automation.Condition]::TrueCondition)) {
        if ($e.Current.ClassName -eq 'cfgTextEdit') {
            try {
                return $e.GetCurrentPattern(
                    [System.Windows.Automation.TextPattern]::Pattern
                ).DocumentRange.GetText(-1)
            } catch { return '' }
        }
    }
    return ''
}
```

### 发送命令（剪贴板粘贴法，绝对可靠）

**不要**用 `SendKeys` 逐字输入——该控件吞字符（实测只进首字母）。
**要**用剪贴板 + `Ctrl+V`：

```powershell
function Send([string]$cmd) {
    [H]::Focus($HWND); Start-Sleep -Milliseconds 350
    [H]::Click($cx, $cy); Start-Sleep -Milliseconds 600
    Set-Clipboard -Value $cmd
    Start-Sleep -Milliseconds 350
    [H]::Ctrl(0x56)            # Ctrl+V
    Start-Sleep -Milliseconds 800
    [H]::Key(0x0D)             # Enter
    Start-Sleep -Seconds 5     # 等命令跑完
}
```

Win32 封装：

```csharp
[DllImport("user32.dll")] public static extern void keybd_event(byte vk, byte scan, uint flags, UIntPtr extra);
public static void Key(byte vk) {
    keybd_event(vk,0,0,UIntPtr.Zero); System.Threading.Thread.Sleep(60);
    keybd_event(vk,0,2,UIntPtr.Zero); System.Threading.Thread.Sleep(120);
}
public static void Ctrl(byte vk) {
    keybd_event(0x11,0,0,UIntPtr.Zero); System.Threading.Thread.Sleep(60);
    keybd_event(vk,0,0,UIntPtr.Zero);   System.Threading.Thread.Sleep(70);
    keybd_event(vk,0,2,UIntPtr.Zero);   System.Threading.Thread.Sleep(60);
    keybd_event(0x11,0,2,UIntPtr.Zero); System.Threading.Thread.Sleep(220);
}
```

读取增量输出：调用前后各取一次 `Console-Text`，用 `$after.Substring($before.Length)`
取新增部分（不要用字符串比较，控制台内容只会追加）。

## 2. 两个必须避开的陷阱

### 陷阱 A：DPI 缩放导致坐标错位

**症状**：`AutomationElement.BoundingRectangle` 返回**物理像素**（2560x1600），
而 `SetCursorPos` 期望的是**逻辑像素**（1707x1067）。两者比例 1.5。

**修法**：进程必须声明 DPI aware，让 UI Automation 与 SetCursorPos 用同一坐标系：

```powershell
[DllImport("user32.dll")] public static extern bool SetProcessDPIAware();
[H]::SetProcessDPIAware() | Out-Null
```

**不修**：点在错误的物理位置上，看起来"点击无效"。这是本会话反复失败的主因之一。

### 陷阱 B：模态对话框吞掉所有点击

**症状**：任何 `mouse_event` 点击、任何 `InvokePattern` 都"成功返回"但界面无变化。

**根因**：当 Fabric Configuration 有**模态子对话框**打开（例如
`Assign New Configuration File`）时，父窗口的按钮对 UIA 仍"可见"，但实际的鼠标
点击被模态窗口拦截。

**判定方法**：枚举所有顶层窗口，找出 `IsModal` 为 true 或标题是对话框的：

```powershell
foreach ($w in [System.Windows.Automation.AutomationElement]::RootElement.FindAll(
        [System.Windows.Automation.TreeScope]::Children,
        [System.Windows.Automation.Condition]::TrueCondition)) {
    Write-Host ("hwnd={0} offscreen={1} name='{2}'" -f `
        $w.Current.NativeWindowHandle, $w.Current.IsOffscreen, $w.Current.Name)
}
```

发现过 **8 个幽灵对话框标题堆在 `y=-22160..-47891`（全部 `offscreen=True`）**，
是历轮自动化残留。处理方法：逐个 `Alt+F4` 关掉，直到只有一个 offscreen 灰色窗口。

**经验**：每次自动化开始前先做「窗口体检」——列出所有顶层窗口，确认没有残留对话框。

## 3. 已验证可用的 GUI 命令序列

在 TCL 控制台里逐条执行（这正是 `scripts/program_sram.tcl` 的内容）：

```
cfg_set_tcl_break -flag true
cfg_connect -ip 127.0.0.1 -port 65420
cfg_set_cable_property -index 0 -freq 1MHz
cfg_scan_chain
cfg_read_device_property -mode 0 -device_index 0
cfg_assign_file -file <绝对路径>/atk_l50_top.sbit -device_index 0
cfg_set_device_property -device_index 0 -program 3
cfg_program -device_index 0
cfg_read_device_property -mode 3
cfg_verify -device_index 0
cfg_read_device_property -mode 3
cfg_disconnect
```

### 频率参数必须带单位

实测报错原文：

```
W: Configuration-4002: Tcl parameter check failed: The input Frequency is not support value,
 The cable is supported : 15 MHz 10 MHz 5 MHz 1 MHz 500 KHz 100 KHz .
```

**必须写 `1MHz`，不能写 `1000000`。** 合法值集：
`15 MHz / 10 MHz / 5 MHz / 1 MHz / 500 KHz / 100 KHz`。

（注意：项目硬约束是统一 1MHz，不要用 15MHz——历史记录显示 15MHz 下载会假成功
`DONE=0`。）

## 4. 文件对话框的坑

`Assign New Configuration File` 对话框：

- **`File name` 框拒绝完整路径**。填绝对路径会报
  `File name "perf_report.sbit" is invalid.`，此时只更新了列表选中项，`File name`
  仍是旧值。
- **正确做法**：先导航到目标目录（`Parent Directory` 按钮坐标为逻辑 (1376,425)），
  再在列表里选中文件，或在 `File name` 里只填**文件名**。
- 列表的 `Date Modified` 列会缓存旧值，**不能**用来判断目录是否已切换。

## 5. 当前阻塞：JTAG 链无器件响应

最后一次运行时，GUI 与 CLI **两条独立路径**给出同一错误：

```
PANGO USB CABLE II cable driver: D2XX DLL
E: JtagServer-0306: No devices detected while scanning the JTAG chain, failed detecting JTAG device chain.
E: Configuration-0008: The command 'Open config cable' execute fail.
E: Configuration-0012: Tcl Command: cfg_scan_chain exec failed.
```

同时的旁证（说明**不是软件/驱动问题**）：

| 检查项 | 结果 | 含义 |
|---|---|---|
| `cfg_set_cable_property -freq 1MHz` | **成功** | 下载器能被打开、能配置 |
| `Cable index 0: USB Cable II` | **枚举到** | FTDI 驱动层正常 |
| `USB Serial Converter A/B` 状态 | **OK** | 设备在系统里在线 |
| `COM8`（板载 CH340）打开 | **成功** | USB 与串口驱动正常 |
| `cfg_scan_chain` | **无器件** | **FPGA 未应答 JTAG** |

**结论**：错误发生在**扫描阶段**，即下载器还在找器件时就失败了。这是物理层问题，
最可能的原因（按可能性排序）：

1. **FPGA 主电源未开或掉电** —— CH340 是 USB 供电的，所以即使主电源关闭，
   `COM8` 依然存在。这**完全符合**观察到的矛盾现象（串口在、JTAG 不在）。
2. JTAG 排线松脱或插反。
3. 芯片被之前的 `cfg_reset_fpga` 置于需重新上电的状态（断电重上电可清除）。

> 历史对照：`scripts/check_gouten.ps1` 早前能成功读到 `STATUSR = 0x001dfca0`，
> 说明当时链路是通的。硬件侧发生过变化。

### 恢复后要做的第一件事

```powershell
Set-Location C:\Users\莫西莫西\Desktop\FPGA项目\fpga_riscv_starter
.\scripts\check_gouten.ps1
```

期望输出 `verdict: IO_ACTIVE` 或至少能读出 `STATUSR`。若仍为 `verdict: UNKNOWN`，
说明链仍未恢复，此时**任何**下载尝试都必然失败，不要再往 GUI 里灌命令。
