# gouten 决定性结论：命令行下载永远无法点亮 IO

> **2026-11-01 撤回本文绝对结论。** 已在同一正常位流复现 Combined/program=3 使 GOUTEN=0，并在断电清除状态后通过非 ISC program=1/readback=1 的 CLI 完成下载、回读、GOUTEN=1 和 CPU UART 验收。问题是特定下载路径，不能归结为 CLI 永远不可用。本文余下内容仅保留为历史；当前方法见 [最终修复记录](2026-11-01_program3输出关闭复现.md)。

日期：2026-10-23
结论：**已由寄存器级证据钉死。命令行下载在 PGL25G 上永远无法使能用户模式输出。**

## 一句话结论

`gouten`（STATUSR bit 17）是用户模式输出使能位。CLI 下载后它恒为 0，所有 IO 引脚停在
高阻态（high-Z），因此板子在串口上永远静默。**这不是固件问题、不是约束问题、不是
波特率问题、不是引脚分配问题**——位流已被正确配置且回读校验通过，只是输出被硬件
门控关闭。必须通过 PDS GUI 的 Program 按钮下载，才会上拉 gouten。

## 证据链

### 1. 厂商工具自己给 bit 17 命名（最强证据）

`C:\pango\PDS_2022.2-SP4.2-ads\bin\cdt_cfg.exe` 内嵌了各芯片族的状态寄存器解码模板。
文件顺序中**第一个**模板（即 PGL25G/Logos 族实际使用的模板）原文是：

```
Bits[29 ..0]
Bit 29:  %1  over_temp
Bit 28:  %1  flg_x32
Bit 27:  %1  flg_x16
Bit 26:  %1  flg_x8
Bit [25-24]: %1 ipal_m[1:0]
Bit 23:  %1  key_lock
Bit 22:  %1  fallback
Bit 21:  %1  dci_match
Bit 20:  %1  pll_lock
Bit 19:  %1  gwen
Bit 18:  %1  grsn
Bit 17:  %1  gouten        <== 用户模式输出使能
Bit 16:  %1  vddt_n
Bit 15:  %1  glogen_fb
Bit 14:  %1  glogen
Bit 13:  %1  done_i
Bit 12:  %1  done
Bit 11:  %1  init_b
Bit  4:  %1  overflow
```

工具在实际运行中打印的正是这个模板，见 `build/cpu_sram_program.log`：

```
The Status Register Code is :00000000000111011111110010100000
Bit 20:  1  pll_lock
Bit 19:  1  gwen
Bit 18:  1  grsn
Bit 17:  0  gouten      <== 唯一为 0 的关键位
Bit 16:  1  vddt_n
Bit 15:  1  glogen_fb
Bit 14:  1  glogen
Bit 13:  1  done_i
Bit 12:  1  done
```

即 `STATUSR = 0x001dfca0`：DONE=1、glogen=1、vddt_n=1、grsn=1、gwen=1、pll_lock=1，
**唯独 gouten=0**。

### 2. 与 GUI 下载的成功样本逐位对照

| 下载方式 | STATUSR | bit 17 gouten | 板上串口 |
|---|---|---|---|
| GUI Program | `0x001ffca0` | **1** | 正常输出（历史已证实） |
| CLI 下载 | `0x001dfca0` | **0** | 零字节 |

两个值的差异**只有 0x20000**，即 bit 17。这不是巧合，而是唯一变量。

### 3. 两个独立读取通道互相印证

`cfg_read_device_property -mode 3`（高层属性）与 `cfg_read_register -address 9`
（原始寄存器）读出**同一个值** `0x001dfca0`，`status_sources_agree = true`。
排除了"读到错位/陈旧寄存器"的可能。

### 4. 写入通道确认无效（不是没试）

对 STATUSR（地址 9）执行 `cfg_write_register` 后，工具报告成功，但重新读取仍是
`0x001dfca0`——**器件静默忽略对状态寄存器的写入**。状态位是只读的，不能靠 CLI 置位。

### 5. 此前所有"CLI 能通"的尝试都被同一位解释

历史记录中反复出现"CLI 下载后 GOUTEN=0 → 四灯全亮/串口静默"，以及大量针对电压约束、
引脚分配、波特率、BSR 观测的实验。这些实验之所以都无法解决，是因为它们都在错误的
层次上找原因：**位流内容完全正确，是配置后的输出门控没打开。**

## 对项目的影响

1. **命令行下载流程无法独立完成上板验证。** 任何需要观察 IO/UART 的验收（CoreMark
   跑分、性能计数读数）都必须走 GUI Program。
2. `scripts/program_sram.ps1` 现在会**显式报告** `gouten_asserted` / `done_asserted` /
   `io_likely_active` 三个字段，并在 gouten=0 时打印醒目告警，避免下游再出现"看起来
   成功但板子没反应"的静默失败。
3. `scripts/check_gouten.ps1`（新增）是只读探针，一条命令即可回答"现在板子会不会说话"。

## 尚未解决的问题

**为什么 GUI 能置位 gouten 而 CLI 不能？** 目前只知道现象与位定义，没有找到 CLI 侧
的等价命令。已排查并排除：

- `cfg_operate_ctl -mode <int>`：需要 mode 整数参数，无文档，合法取值未知（传非整数报
  `E: Flow-0079`）。未逐一穷举 mode 值。
- `cfg_debug_operate -mode <int>`：同上。
- `cfg_set_options -mode`：报 `E: Flow-0073: Option '-mode' is not defined`，不是它的选项。
- 在 `cdt_cfg.exe` / `cdt_cfg_shell.exe` 字符串中搜索 `gouten`：仅出现在**状态解码
  模板**与显示格式串中，**没有任何写入/使能 gouten 的命令名**。这强烈暗示 gouten 的
  使能是 GUI 在配置完成后通过一条独立时序/私有命令完成的，或由 GUI 特有的配置模式
  （如 `Configuration Method` 的选择）决定。

## 可复现命令

```powershell
# 只读探针：现在板子会不会说话？
cd fpga_riscv_starter
& .\scripts\check_gouten.ps1
& .\scripts\check_gouten.ps1 -Json

# 命令行下载（会明确报告 gouten 状态并告警）
& .\scripts\program_sram.ps1 -Target cpu -FirmwareApp perf_report
```

## 硬约束提醒

- **不要写 Flash / eFuse。** 本流程只做 SRAM 配置。
- **不要用 15MHz 下载**：会报假成功而 DONE=0。统一 1MHz。
- 工具报 `successfully` **不等于**验证通过；必须看 DONE + STATUSR + gouten。
- 对 `C:\fpga\` 与 `C:\pango\` 的读写可能需要提权。
- 工作目录必须是纯 ASCII 路径；vendor 工具同时校验 `-work_dir` 与**进程实际工作
  目录**，因此 PowerShell 里必须用 `[IO.Directory]::SetCurrentDirectory()`，
  `Push-Location` 不改变进程 cwd、无效。
